# Genery Hub: конструктор личного интерфейса из виджетов

План архитектуры и MVP. Кода здесь нет — только решения, модель данных, правила безопасности и этапы.

## 1. Идея в двух абзацах

Сейчас у всех пользователей Genery одинаковое меню (`src/pages/menu/Menu.jsx`): баннер, цитата дня и шесть плиток-ссылок. Мы хотим, чтобы у каждого была **своя главная страница**. При первом входе пользователь видит стартовый набор виджетов. Дальше он собирает интерфейс сам: перетаскивает плитки по сетке, меняет их размер, добавляет и удаляет виджеты из каталога. Или пишет ИИ «сделай виджет, который…».

Главный принцип: **виджет — это тип плюс конфиг.** Тип (React-компонент) пишем мы и проверяем. Пользователь и ИИ меняют только конфиг — JSON, который проверяется по схеме. Произвольный код от ИИ появляется только на позднем этапе и запускается в изолированном iframe без доступа к аккаунту.

## 2. Что уже есть в проекте

| Раздел | Маршрут | Источник данных | Каким виджетом может стать |
|---|---|---|---|
| Расписание | `/timetable/:id` | `groups/{id}/info/timetable` | **«Сейчас урок»** (текущий и следующий урок, кабинет, таймер до звонка), 2×1 / 2×2 |
| Столовая | `/canteen-occupancy` | `canteens/{id}`, `devices` + `days` | **«Столовая»**: кольцо заполненности и «освободится к…» (готовые расчёты в `canteenStats.js`), 1×1 / 2×1 |
| Калькулятор заказа | `/order-calculator` | локальное меню | **«Быстрый заказ»**: кнопка-ссылка или мини-калькулятор, 1×1 |
| Чаты | `/chats`, `/chat/:id` | `chats` | **«Чаты»**: последние 3 чата с непрочитанными, 2×2; или «Закреплённый чат», 1×1 |
| Цитата дня | `/qoutes` | `menu/qoutes.js` (локально) | **«Цитата дня»** — уже готовый `InfoBlock`, 2×1 |
| Обновления / новости | `/updates`, `/posts` | `Updates.js`, `posts` | **«Лента»**: 2–3 последних поста, 2×2 |
| Игры | `/game-menu`, `/tapcoin`, `/rocket`, `/flippybird`, `/guessline`, `/quiz`, `/casino` | частично `users/.../preferences` (монеты) | **«Игра»** — плитка-запуск с рекордом; Tapcoin можно встроить прямо в плитку |
| Монеты / магазин | `/shop`, `/cashback` | `users/{uid}/info/preferences` | **«Баланс»**: монеты и ссылка в магазин, 1×1 |
| Файлы группы | `/download/:id` | `groups/{id}/info/downloads` | **«Файлы группы»**: последние загрузки, 2×1 |
| Профиль, группы, рейтинг | `/profile`, `/group-list`, `/rating` | `users`, `groups` | **«Мой профиль»** (аватар, группа), **«Рейтинг»** (топ-5) |
| Ссылка | — | — | **«Ярлык»** на любой маршрут: иконка, подпись, цвет. Заменяет нынешние `Block` |

Что пригодится из текущего кода:
- `Block` / `InfoBlock` / `BannerBlock` — первые виджеты-ярлыки почти без изменений.
- Темы (`src/themes/Themes.js`, контекст `ElementProvider`) — виджеты берут цвета из `theme`, а не задают их сами. Так конструктор сразу работает во всех темах.
- Страница столовой уже сделана в нужном стиле: модульная сетка, плитки со скруглением 28px, SVG-иконки через `Icon`. Это эталон для оформления виджетов.
- `framer-motion` уже в зависимостях — подойдёт для анимаций перетаскивания.

Что мешает и что надо учесть:
- `ElementProvider.jsx` экспортирует `useTheme`, который ссылается на несуществующий `ThemeContext`. Хук сломан, виджеты должны брать тему через `useContext(ElementContext)` (или хук нужно починить).
- Каждая страница сама выставляет `elementColors` (шапка, футер, фон). Виджет — это не страница, он не должен трогать `elementColors`.
- Данные грузятся прямо в компонентах страниц (`getDoc` внутри `useEffect`). Для виджетов нужно вынести загрузку в хуки (`useTimetable(groupId)`, `useCanteen(id)`). Тогда страница и виджет будут использовать одни и те же данные. Для столовой это уже почти сделано: `CanteenView` получает всё через пропсы.
- В `paths.jsx` маршрут `/order-calculator` объявлен дважды — мелочь, но при переходе на реестр стоит убрать.
- Своего сервера нет, ИИ-код в `messenger/AI.jsx` закомментирован. Ключи ИИ нельзя держать во фронтенде (см. раздел 5).


### Реестр типов виджетов

Один файл `src/widgets/registry.js`. Каждый тип описан так:

```js
{
  type: 'canteen',                // уникальный id, никогда не меняется
  version: 2,                     // версия схемы конфига
  title: 'Столовая',
  icon: 'users',                  // имя SVG-иконки из общего набора
  sizes: ['1x1', '2x1'],          // разрешённые размеры плитки
  defaultSize: '2x1',
  schema: canteenSchema,          // JSON Schema конфига
  defaults: { canteenId: 'main', show: 'free' },
  migrate: { 1: cfg => ({ ...cfg, show: 'free' }) },  // v1 → v2
  component: lazy(() => import('./canteen/CanteenWidget.jsx')),
  aiHint: 'Показывает свободные места в столовой и прогноз', // описание для ИИ
  requires: [],                   // например ['mainGroup'] для расписания
}
```

Плюсы такого подхода:
- Каталог, ИИ и проверка конфигов работают от одного источника.
- Новый виджет = новая папка и одна строка в реестре.
- Ленивая загрузка: пользователь скачивает код только тех виджетов, которые у него стоят.

### Сетка

- Сетка с фиксированным числом колонок: 4 на телефоне, 8 на широком экране. Высота ряда равна ширине колонки, поэтому 1×1 — квадрат. Отступ 12px, как на странице столовой.
- Размеры плиток берутся из набора `1x1, 2x1, 2x2, 4x2` и т. п., а не свободные. Так любая раскладка аккуратно ложится в сетку.
- Библиотека: **`react-grid-layout`** (готовые drag, resize, responsive и сериализация координат) или **`@dnd-kit`** плюс своя упаковка. Рекомендую `react-grid-layout` для MVP: экономит 1–2 недели. Ей нужна проверка на тач-устройствах. Альтернатива — своя сетка на CSS Grid с `@dnd-kit/sortable`, если важен полный контроль над видом.
- Два режима: **просмотр** (плитки кликабельны, ведут в разделы) и **правка** (включается долгим нажатием или кнопкой; плитки покачиваются, появляются ручки размера и кнопка «удалить»).
- Каждый виджет обёрнут в `WidgetFrame` с error boundary. Упавший виджет показывает «Не удалось загрузить» и не роняет всю страницу.

### Оформление виджетов

- Плитка: скругление 28px, фон `theme.element_first_color`, акцент `#0040F9`, лайм `#C3F82B` для «хорошо / свободно», красный `#FF4365` для «плохо / занято».
- Только SVG-иконки из общего набора `src/widgets/icons.js`. Сейчас набор `ICONS` живёт внутри `CanteenView.jsx` — его стоит вынести. Никаких эмодзи.
- Пользователь может выбрать цвет плитки только из палитры темы (поле `color: 'accent' | 'lime' | 'tile' | ...`), а не любой hex. Так интерфейс остаётся единым.

## 4. Модель данных (Firestore)

### Почему не `users/{uid}/layout`

По текущим правилам (`firmware/firestore-rules-counter.txt`) **любой вошедший пользователь может записывать в любую коллекцию**, кроме `admins`, `devices`, `canteens`, `firmware`. Это общее правило `match /{collection}/{rest=**}`. В Firestore разрешения складываются через «ИЛИ»: если положить раскладку в `users/{uid}/layout`, никакое отдельное правило не помешает другому пользователю её перезаписать. Вписать `users` в исключения тоже нельзя: сейчас приложение пишет в `users/{чужой uid}/info/preferences` (подписки, чаты — `OtherUserProfile.jsx`, `ChatEdit.jsx`).

Поэтому раскладки хранятся в **новой отдельной коллекции `layouts`**, которую мы добавим в список исключений общего правила.

### Документы

**`layouts/{uid}`** — раскладка пользователя (один документ, читается за один запрос):

```js
{
  schemaVersion: 1,             // версия формата всего документа
  rev: 17,                      // счётчик сохранений (защита от гонок между вкладками)
  updatedAt: Timestamp,
  template: 'student-default',  // от какого стартового набора начали
  breakpoints: {
    mobile:  { cols: 4, items: [ { i: 'w_a1', x: 0, y: 0, w: 2, h: 1 }, ... ] },
    desktop: { cols: 8, items: [ ... ] }
  },
  widgets: {
    w_a1: { type: 'canteen',   v: 2, config: { canteenId: 'main', show: 'free' }, color: 'accent' },
    w_b7: { type: 'timetable', v: 1, config: { groupId: null /* = основная группа */ } },
    w_c3: { type: 'shortcut',  v: 1, config: { route: '/game-menu', label: 'Игры', icon: 'gamepad' } },
    w_d9: { type: 'note',      v: 1, config: { text: 'Сдать реферат до пятницы' } }
  }
}
```

- Координаты (`breakpoints`) отделены от содержимого (`widgets`). Перетаскивание меняет только координаты, правка настроек — только один виджет.
- Ограничения: не больше 40 виджетов и 20 КБ на конфиг. До лимита документа Firestore в 1 МБ далеко.
- Сохранение с задержкой (debounce) около 800 мс после окончания перетаскивания, один `setDoc` с `merge`.

**`layoutTemplates/{templateId}`** — стартовые наборы. Читают все, меняют только администраторы. Например `student-default`, `teacher-default`. При первом входе, если `layouts/{uid}` нет, клиент копирует шаблон.

**`layouts/{uid}/history/{autoId}`** (по желанию) — последние 10 сохранений для «Отменить» и «Вернуть как было». Старые записи удаляет клиент или функция.

**`miniApps/{appId}`** (этап 3) — мини-приложения: `{ ownerUid, title, status: 'draft'|'private'|'shared'|'blocked', bundlePath, createdAt, model, promptHash }`. Код лежит в Cloud Storage, а не в Firestore.

**`widgetData/{uid}/{widgetId}`** (по необходимости) — данные, которые виджет копит сам: рекорд игры, список дел, заметки длиннее лимита конфига. Держим их отдельно от раскладки, чтобы частые записи (например, клики в Tapcoin) не перезаписывали всю раскладку.

### Версионирование

Три независимых уровня:
1. **`schemaVersion` документа** — формат всей раскладки. Меняется редко, миграцию выполняет клиент при чтении.
2. **`v` у каждого виджета** — версия схемы конфига типа. При загрузке, если `v < registry[type].version`, по цепочке выполняется `migrate[v]`. Результат сохраняется при следующей записи.
3. **Неизвестный тип** (удалили из реестра или пользователь открыл старую версию сайта) — виджет **не удаляется**, а показывается как плитка «Виджет недоступен». Его данные сохраняются.

Все конфиги перед сохранением и перед показом проверяются по JSON Schema (`ajv`, около 30 КБ, или лёгкий `zod`, если удобнее писать схемы кодом). Если конфиг не проходит проверку, подставляются `defaults` этого типа.

## 5. ИИ-виджеты и безопасность

### Где живёт ИИ

Ключи OpenAI и Gemini **нельзя класть во фронтенд**: их сразу вытащат из бандла. Нужна серверная функция. Варианты:
- **Firebase Cloud Functions** (callable). Знает пользователя через `context.auth`, ключ хранится в Secret Manager. Нужен тариф Blaze.
- **Vercel Function**. Проверка Firebase ID-токена через `firebase-admin`.

`genkit` и `@genkit-ai/googleai` уже есть в зависимостях и хорошо подходят именно для серверной части (структурированный вывод по схеме). Из фронтенд-зависимостей их потом можно убрать.

Лимиты на стороне функции: например, 20 генераций в день на пользователя (счётчик в `aiUsage/{uid}`, запись только из функции). Длина запроса — до 500 символов.

### Этап A: ИИ собирает конфиг из готовых типов (кода нет)

```
Пользователь: «хочу плитку, которая показывает, сколько минут до конца урока, лаймовая»
        │
        ▼
generateWidgetConfig(prompt)
   1. В системный промпт подставляются type, title, aiHint и schema всех типов из реестра
   2. Модель отвечает строго по схеме ответа (structured output):
        { type, size, color, config, title, explanation }
   3. Функция проверяет: type есть в реестре, config проходит JSON Schema,
      size ∈ sizes, color ∈ палитры. Если нет — одна повторная попытка с текстом ошибки
   4. Возвращает готовый виджет. Сама в базу ничего не пишет
        │
        ▼
Клиент показывает живое превью → пользователь жмёт «Добавить» → обычное сохранение
```

Почему это безопасно:
- ИИ выбирает только из того, что мы уже написали и проверили. Ни одна строка от модели не выполняется как код.
- Строковые поля конфигов (подписи, текст заметки) выводятся как текст React, без `dangerouslySetInnerHTML`. В схемах — `maxLength` и запрет HTML.
- Поле `route` у ярлыков разрешает только маршруты из `paths.jsx`. Внешние ссылки — только `https://` с подтверждением при переходе.
- Если подходящего типа нет, ИИ так и отвечает («такого виджета пока нет, вот ближайший»). Такие запросы стоит логировать — это готовый бэклог новых типов.

Помимо одного виджета, ИИ может предложить **всю раскладку** («собери мне главную для подготовки к ОРТ») — тот же механизм, только на выходе массив виджетов.

### Этап B: мини-приложения в песочнице (настоящий код)

Пользователь просит «сделай игру, где надо ловить буквы», и ИИ пишет HTML/JS. Это код, поэтому правила строже:

1. **Изоляция.** Мини-приложение показывается в `<iframe sandbox="allow-scripts">` **без** `allow-same-origin`. У него «пустой» origin: нет доступа к cookies, localStorage, IndexedDB Genery и к токену Firebase. Лучше всего отдавать его с отдельного домена (например `apps.genery-usercontent.web.app`), а не через `srcdoc` с основного.
2. **CSP внутри iframe:** `default-src 'none'; script-src 'unsafe-inline' https://cdn.jsdelivr.net (белый список); style-src 'unsafe-inline'; img-src data: blob:; connect-src 'none'`. Мини-приложение не может отправлять данные наружу.
3. **Мост `postMessage`** с узким API, который хост проверяет по `event.source`:
   `getTheme()`, `getSize()`, `storage.get/set(key)` (до 100 КБ в `widgetData/{uid}/{widgetId}` — пишет хост, а не iframe), `resize()`, `openRoute(route)` (только маршруты из белого списка).
   Ни `uid`, ни email, ни данных других пользователей мини-приложение не получает.
4. **Проверка перед публикацией:** функция прогоняет код через статический фильтр (запрет `top.`, `parent.location`, `document.cookie`, внешних `fetch` и т. п. — это не защита, а ранний отказ) и лимит размера (до 200 КБ).
5. **Доступ.** По умолчанию мини-приложение видит только автор (`status: 'private'`). Чтобы поделиться (`shared`), нужна модерация администратором. Кнопка «Пожаловаться», администратор может поставить `blocked`.
6. **Ресурсы.** iframe легко подвесить бесконечным циклом. Хост показывает «Приложение не отвечает — перезапустить» по пингу через `postMessage`. Мини-приложения запускаются только по нажатию на плитку, а не автоматически при загрузке главной.

## 6. Правила Firestore

Изменения к текущему файлу `firmware/firestore-rules-counter.txt`:

```
// 1) Добавить новые коллекции в исключения общего правила записи
match /{collection}/{rest=**} {
  allow write: if isUser()
    && !(collection in ['admins', 'devices', 'canteens', 'firmware',
                        'layouts', 'layoutTemplates', 'widgetData', 'miniApps', 'aiUsage']);
}

// 2) Раскладка: только владелец
match /layouts/{uid} {
  allow write: if isUser() && request.auth.uid == uid
    && request.resource.data.keys().hasOnly(['schemaVersion','rev','updatedAt','template','breakpoints','widgets'])
    && request.resource.data.widgets.size() <= 40
    && request.resource.data.rev is int
    && (resource == null || request.resource.data.rev == resource.data.rev + 1);

  match /history/{entry} {
    allow write: if isUser() && request.auth.uid == uid;
  }
}

// 3) Шаблоны: читают все, меняет администратор
match /layoutTemplates/{id} {
  allow write: if isAdmin();
}

// 4) Данные виджетов: только владелец
match /widgetData/{uid}/{rest=**} {
  allow write: if isUser() && request.auth.uid == uid;
}

// 5) Мини-приложения: создаёт и пишет только Cloud Function (Admin SDK обходит правила);
//    клиенту запись запрещена совсем, блокирует администратор
match /miniApps/{appId} {
  allow update: if isAdmin()
    && request.resource.data.diff(resource.data).affectedKeys().hasOnly(['status']);
}
// aiUsage — запись только из функции, клиентских правил записи нет
```

Открытый вопрос: **чтение**. Сейчас общее правило `allow read: if isUser()` открывает всё всем, и закрыть отдельную коллекцию из-за сложения через «ИЛИ» нельзя. Раскладки и записки пользователей будут видны другим вошедшим пользователям, если читать базу напрямую. Варианты:
- (а) смириться: раскладка не секрет;
- (б) переписать общее правило чтения на список коллекций (`collection in [...]`, исключив `layouts`, `widgetData`, `miniApps`, `aiUsage`). Это аккуратнее, но потребует проверить все запросы, особенно `collectionGroup` в поиске.

Рекомендую (б) на этапе 1, если в виджетах будут заметки или списки дел.

Правила нужно проверить в Firebase Emulator: чужой uid не может писать в `layouts`, анонимная плата не может писать никуда, кроме своих счётчиков, `rev` растёт строго на 1.

## 7. MVP: стартовый набор виджетов

Восемь типов. Все строятся на уже существующих данных:

| # | Тип | Размеры | Источник | Сложность |

| 1 | `shortcut` — ярлык на раздел (иконка, подпись, цвет) | 1×1, 2×1 | маршруты | низкая |

| 5 | `quote` — цитата дня | 2×1 | `qoutes.js` | низкая |

## 8. Этапы и оценка

Оценки даны для одного разработчика, который знает проект, в неделях работы.

| Этап | Что входит | Оценка |
|---|---|---|
| **0. Подготовка** | Вынести загрузку данных из страниц в хуки (`useTimetable`, `useCanteen`, `useChats`, `useBalance`); общий набор SVG-иконок; починить `useTheme`; убрать дубль маршрута; Firebase Emulator для правил | 1 нед. |
| **1. MVP** | `HubPage` вместо `Menu` на `/menu` (старое меню за флагом на время перехода); сетка с drag/resize и режимом правки; реестр, `WidgetFrame`, error boundary; 8 виджетов; `layouts/{uid}` + шаблон + миграции; каталог; новые правила; «Сбросить к стандартной» | 3–4 нед. |
| **2. ИИ-конфигурация** | Серверная функция с ключом и лимитами; генерация виджета и целой раскладки по схемам реестра; превью перед добавлением; лог запросов «нет такого типа» | 1,5–2 нед. |
| **3. Мини-приложения** | Отдельный домен-песочница, iframe + CSP, мост `postMessage`, хранилище `widgetData`, генерация кода, статический фильтр, приватные и общие приложения, модерация администратором | 3–4 нед. |
| **4. Документы и презентации** | Виджеты-генераторы: «документ в стиле …» и «презентация». ИИ выдаёт **структурированный JSON** (разделы и блоки / слайды и макеты), а наш рендерер собирает из него страницу или слайды в стиле Genery. Экспорт в PDF (печать из браузера) и `.pptx` (`pptxgenjs`), хранение в Storage, виджет «Мои документы» | 3–4 нед. |

Итого до MVP — около 4–5 недель, до ИИ-конфигурации — 6–7 недель, полный объём — 12–15 недель.

Документы и презентации тоже строятся по принципу «ИИ генерирует данные, а не код». Поэтому этап 4 можно делать параллельно с этапом 3 или раньше него.

## 9. Риски

- **Перетаскивание на телефоне** конфликтует с прокруткой. Правка только в режиме правки, перетаскивание после долгого нажатия.
- **Производительность**: 10 виджетов с отдельными `onSnapshot` дают 10 подписок. Общие данные (расписание группы, столовая) берём из общего кэша хуков, а не загружаем в каждом виджете.
- **Стоимость ИИ**: лимиты на пользователя и дешёвая модель для конфигов (структурированный вывод не требует топовой модели), мощная — только для мини-приложений и документов.
- **Открытые правила чтения** (см. раздел 6).
- **Ключ Firebase в `firebase.js` и прошивке** — это нормально (это публичный идентификатор проекта), но вся защита держится на правилах. Изменения правил нужно проверять в эмуляторе до публикации.

## 10. Вопросы владельцу

1. Конструктор **заменяет** нынешнее меню на `/menu` или живёт рядом (например `/hub`), пока пользователи привыкают?
2. Разные стартовые наборы для учеников, учителей и администрации — или один на всех? Откуда брать роль (сейчас есть только `admins`)?
3. Можно ли делиться раскладками и виджетами («скопировать главную друга», «опубликовать мини-игру для группы»)? От этого зависят правила чтения и модерация.
4. Нужна ли синхронизация раскладки между телефоном и компьютером или достаточно одной раскладки на устройство?
5. Какой ИИ-провайдер основной (OpenAI или Gemini) и какой месячный бюджет? Готовы ли перейти на тариф Firebase Blaze ради Cloud Functions — или сервер будет на Vercel?
6. Кто модерирует общие мини-приложения и что делать с жалобами?
7. Документы «в заданном стиле» — это стиль Genery, стиль школы (шаблоны рефератов и докладов) или любой стиль по описанию? Нужен ли экспорт в Word?
8. Закрываем ли чтение чужих раскладок и заметок (переписать общее правило чтения) — да или нет?
9. Сколько минимум должно остаться в раскладке: можно ли удалить вообще всё, или расписание и чаты обязательны?
